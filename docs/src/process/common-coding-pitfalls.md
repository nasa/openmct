# Common Coding Pitfalls

Guidance that applies to all code contributed to Open MCT, whether written by a
person or generated by a tool. It complements the code standards in
[CONTRIBUTING.md](../../../CONTRIBUTING.md) with the mistakes that come up most
often in review.

## General principles

- All code must follow "Clean Code" principles as described by Robert C. Martin.
- Document all public API with TypeScript-aware doc comments. Use TSDoc
  conventions so that consumers can rely on TypeScript when writing plugins.
- Self-documenting, descriptive code is always preferable to comments. Comments
  are appropriate only where something unexpected is happening that cannot be
  adequately captured through clear function and variable naming, or through
  function decomposition.

## Clarity

- Write code like you are writing a children's book. It should be tediously
  clear what you are doing. Write code for future you, who is trying to parse it
  at 11pm before a deadline with no sleep the night before.
  - Prefer long but clear variable and function names over short ones.
  - Do not use tricks and shortcuts. Even simple ones like `!!thing` require a
    little more cognitive power than `thing !== undefined`.
  - Do not use complex or nested ternaries.
- In a trade-off between clarity and brevity, always favor clarity. Clear code
  might be more verbose, but verbose code can always be broken up into separate
  functions.

  Bad example:

  ```js
  function makeCoffee(teaspoonsOfSugar) {
    addGrounds();
    addWater();

    return teaspoonsOfSugar > 0 ? addSugar(teaspoonsOfSugar) && serve() : serve();
  }
  ```

  Good example:

  ```js
  function makeCoffee(teaspoonsOfSugar) {
    addGrounds();
    addWater();

    if (teaspoonsOfSugar > 0) {
      addSugar(teaspoonsOfSugar);
    }

    return serve();
  }
  ```

- Truthiness is not a good substitute for truth.

  Bad example:

  ```js
  if (thing) {
    doSomething();
  }
  ```

  Good example:

  ```js
  if (thing !== undefined) {
    doSomething();
  }
  ```

## Functions

- Functions should do one thing.
- Functions should not have unexpected side effects.
  - Any function whose name starts with `get` should never mutate anything.
  - Functions should do what their name says, and nothing else.
  - Functions should not mutate anything outside of their scope unless they are
    a member function (for example, a Vue method). In those cases the name
    should make it clear that a change will take place when it is called
    (`setThing`, `updateThing`).
- Do not use flags as function parameters.
- Keep functions short: 20 lines or less.
- Functions should be descriptively named, even if the name is long. Imagine
  you are writing a story.
- Event handlers should be named for what they do, not for the event they
  handle.

  Bad example:

  ```html
  <button @click="handleClick"></button>
  ```

  Good example:

  ```html
  <button @click="addRow"></button>
  ```

- Order functions from the highest level of abstraction to the lowest. Yes,
  this implies deferred function definition.

  ```js
  makeCoffee(2);

  function makeCoffee(teaspoonsOfSugar) {
    addGrounds();
    addWater();
    addSugar(teaspoonsOfSugar);
  }

  function addGrounds() {
    // ...
  }

  function addWater() {
    // ...
  }

  function addSugar(teaspoonsOfSugar) {
    // ...
  }
  ```

- Do not write guard code for things that should never happen. Fail fast so we
  can find bugs.

  Bad example:

  ```js
  function capitalizeObjectName(object) {
    if (object === undefined) {
      return;
    }

    openmct.objects.mutate(object, 'name', object.name.toUpperCase());
  }
  ```

  Good example:

  ```js
  function capitalizeObjectName(object) {
    openmct.objects.mutate(object, 'name', object.name.toUpperCase());
  }
  ```

## Working with the Open MCT API

- Use `openmct.objects.get` as rarely as possible.
  - Views get an object passed to them. Use that if you can.
  - It is generally only necessary when an object has a stored reference to
    another object identifier (for example, notebooks and conditionals).
  - The currently navigated object is available from the router if for some
    reason you do not have a reference to the view object.
  - The composition API returns child objects.
- Be careful of anything that happens in a subscribe callback. Assume any code
  invoked by a subscribe callback runs multiple times per second, multiplied by
  100 telemetry points.
- `setTimeout` is a code smell. If you are tempted to use `setTimeout` or
  `setInterval`, there is probably a better way. If you cannot think of one,
  discuss it with a colleague.
- Use resize and scroll events very carefully. They fire extremely rapidly. If
  you have to use them, optimize the callback as much as you can and throttle
  it (using `requestAnimationFrame`, `_.throttle`, or `_.debounce`).
- If you find yourself doing an exhaustive array scan, ask whether there is a
  better approach. Could you use a map, or track an index value?

  Bad example:

  ```js
  function showNextThing(thing) {
    let indexOfThing = searchForThing(thing);
    let nextThing = this.allTheThings[indexOfThing + 1];
    showThing(nextThing);
  }
  ```

  Good example:

  ```js
  function showNextThing() {
    let nextThing = this.allTheThings[this.indexOfThing++];
    showThing(nextThing);
  }
  ```

  Sometimes array scans are unavoidable. In that case, think about whether
  anything could be done to improve search efficiency. For example, if the
  elements of an array are kept sorted, a binary search finds an element in
  O(log N) in the worst case, versus O(N) for an exhaustive search of an
  unsorted array.

## Vue

- Do not invoke methods from Vue templates. There is almost always a better
  way. Use computed properties where possible.

  Bad example:

  ```html
  <div v-for="datum in telemetryData">
    {{ getTimestamp(datum) }}
  </div>
  ```

  Your problem may be solved by creating a view-specific model of the data you
  are trying to show. When data is received, build a new model that already
  includes the formatted timestamp:

  ```html
  <div v-for="datum in viewData" :key="datum.key">
    <telemetry-row :datum="datum" />
  </div>

  <!-- TelemetryRow.vue -->
  <div>{{ formattedDate }}</div>
  ```

  ```js
  computed: {
    formattedDate() {
      return this.dateFormatter.format(this.datum);
    }
  }
  ```

- `index` cannot be used as the key in `v-for`. Use something unique about the
  value in each row. Combine multiple attributes to create a unique key if
  necessary (for example, timestamp plus telemetry value). You will probably
  need a view-specific model for this; see the previous point for an example.
- Avoid code that makes the API reactive. Vue reactivity spreads like a virus
  into any object attached as a data attribute or passed as a prop to a Vue
  component. Use `inject` to pass the API down, and do not alias any part of it
  from `data`.

## Organization

- Organize source code by what it does, not by file type. Do not put all of the
  Vue components in one directory (Telemetry Table is the anti-pattern here).

  Bad organization:

  ```text
  myTablePlugin
  ├── components
  │   ├── TableRow.vue
  │   ├── TableColumn.vue
  │   └── Table.vue
  └── src
      ├── TableRow.js
      ├── TableColumn.js
      └── Table.js
  ```

  Good organization:

  ```text
  myTablePlugin
  ├── rows
  │   ├── TableRow.vue
  │   └── TableRow.js
  ├── columns
  │   ├── TableColumn.vue
  │   └── TableColumn.js
  └── table
      ├── Table.vue
      └── Table.js
  ```
